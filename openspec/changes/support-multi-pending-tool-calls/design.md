## Context

当前 AI 会话流程以“单个未响应工具”为核心假设。`DefaultAiService.processConversationLoop()` 在拿到一轮 `toolCalls` 后，会按顺序逐个遍历，但一旦遇到需要确认的工具或 `ask_human`，就立即返回；`ChatMemory.currentNotRespondedTool()` 也只会从最后一条 assistant message 中找出一个未响应工具。这导致同一轮中其余工具调用既没有发送到前端，也没有在恢复时补齐响应。

本次变更会同时影响 `spectre-core` 的工具调用与恢复逻辑，以及 `spectre-frontend` 的 AI 工具消息展示与交互。设计需要满足以下约束：

- 继续依赖 `chatMemory` 作为恢复上下文来源，不额外引入批次 ID。
- 恢复时必须保证 `ToolResponseMessage.responses` 的数量和顺序与 assistant 原始 `toolCalls` 完全一致。
- 前端需要同时展示多个确认项，但多个 `ask_human` 只允许逐个回答，避免用户并发填写造成上下文混乱。

## Goals / Non-Goals

**Goals:**

- 支持单轮 assistant 返回多个 `tool_call` 时的整批挂起与整批恢复。
- 为每个工具调用提供稳定的 `toolCallId`，让前后端都能精确关联同名工具的不同实例。
- 在存在阻塞型工具时，先把全部工具调用一次性发送到前端，再由前端处理完整批次后恢复会话。
- 恢复阶段按原始顺序统一执行工具、生成完整 `ToolResponseMessage`，然后继续调用 LLM。

**Non-Goals:**

- 不改变现有 LLM 模型选择、token 统计或技能装载逻辑。
- 不引入新的持久化存储来保存待恢复批次状态。
- 不支持“部分提交后局部恢复”流程；一个批次必须在前端全部处理完成后再恢复。

## Decisions

### 1. 使用“最后一条未完成 assistant message”作为唯一恢复上下文

后端不引入 `batchId`，而是继续从 `chatMemory` 中定位最后一条尚未被完整响应的 assistant message，并将其 `toolCalls` 视为当前待恢复批次。

这样做的原因：

- 恢复目标在单会话内天然唯一，增加 `batchId` 只会放大协议复杂度。
- `chatMemory` 已经是当前实现的真实上下文来源，沿用这条链路最符合现有架构。

备选方案：

- 为每个批次生成额外 `batchId` 并随事件传给前端。该方案在当前会话模型中缺乏必要性，因此不采用。

### 2. 阻塞批次内所有工具先进入待处理状态，不提前执行普通工具

只要同一轮 `toolCalls` 中存在 `requireConfirm` 或 `ask_human`，后端就不立即执行任何工具，而是把全部工具统一发送给前端。其中普通工具被标记为“等待执行”，在前端处理完整批次后才真正执行。

这样做的原因：

- 可以彻底避免“部分工具已执行、部分工具挂起”导致的恢复语义分裂。
- 恢复阶段只需要按原始顺序走一遍，就能得到完整、稳定的工具响应列表。

备选方案：

- 先执行普通工具，再挂起阻塞工具。该方案实现较快，但会让恢复阶段同时处理“已执行结果”和“待执行工具”，状态更复杂，因此不采用。

### 3. 事件协议从“单工具流”升级为“批量开始 + 单工具状态”

后端在检测到阻塞批次时，先发出一次批量开始事件，携带该轮全部工具调用及其初始状态。每个工具至少包含 `toolCallId`、`toolName`、`arguments`、`status`。

推荐前端展示状态：

- `PENDING_EXECUTION`
- `PENDING_CONFIRM`

同时保留单工具完成事件，用于恢复执行后把每个工具的结果逐个回推到前端。

这样做的原因：

- 前端可以天然识别“这些工具属于同一轮”并保持原始顺序。
- `toolCallId` 可以稳定关联多个同名工具，不再依赖 `toolName` 推断。
- `ask_human` 本身已经有稳定的工具名，直接用 `toolName == "ask_human"` 判定会比额外维护第三种 pending 状态更简单。

备选方案：

- 保留多个 `onToolCallStart` 事件，让前端自己推断批次边界。该方案对现有 UI 侵入较小，但边界推断脆弱，因此不采用。

### 4. 前端一次性提交整批结构化响应，后端再统一执行

前端完成所有确认和人工回复后，以原始顺序提交完整数组：

```json
[
  {
    "toolCallId": "foo",
    "content": "YES"
  },
  {
    "toolCallId": "bar",
    "content": "用户回复"
  },
  {
    "toolCallId": "baz",
    "content": ""
  }
]
```

后端恢复时执行以下校验：

- 提交数量必须等于 assistant message 的 `toolCalls.size`
- 每项 `toolCallId` 必须与原始顺序一致
- 每项都必须提供 `content` 字段，避免 Kotlin 侧引入额外空值分支
- `PENDING_CONFIRM` 的 `content` 只能是 `YES` 或 `NO`
- `toolName == "ask_human"` 的 `content` 必须为非空文本
- `PENDING_EXECUTION` 的 `content` 必须为 `""`

随后按原始顺序处理：

- `YES`：执行确认型工具
- `NO`：生成拒绝响应文本
- `ask_human`：直接使用人工回复作为工具响应
- `PENDING_EXECUTION`：在此阶段执行普通工具

这样做的原因：

- 恢复接口保持幂等且简单，不需要支持部分提交。
- `ToolResponseMessage` 可以一次性构造完整响应，严格满足 Spring AI 的工具响应配对要求。

备选方案：

- 前端逐项提交，每收到最后一项再自动恢复。该方案前端交互更即时，但后端仍需要维护批次内中间状态，复杂度更高，因此不采用。

### 5. ask_human 在批次内串行展示，但仍属于同一次整批恢复

前端在同一批次中如果存在多个 `toolName == "ask_human"` 的工具，只展示第一个待回答项；当用户提交后，再展示下一个，直到全部回答完成。尽管展示是串行的，但恢复请求仍然一次性提交整批结果。

这样做的原因：

- 多个开放式问题并发显示会显著增加用户负担，并且容易让回答错位。
- 后端依旧保留“整批恢复”的单一语义，不需要引入半批次状态。

## Risks / Trade-offs

- [前后端协议一起变化] → 先在事件和请求结构中新增 `toolCallId` 与状态字段，由前端优先兼容新字段，避免联调期间完全不可用。
- [阻塞批次中的普通工具执行被延后] → 在设计中明确这是预期行为，并通过前端“等待执行”状态向用户解释工具尚未开始执行。
- [恢复接口对顺序和数量要求严格] → 在后端提供明确校验错误信息，帮助前端快速发现组装错误。
- [多个 ask_human 串行展示可能拉长交互时间] → 保持同批次一次性恢复，减少多次往返带来的额外状态复杂度。
